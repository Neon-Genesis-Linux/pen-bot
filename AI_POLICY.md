# AI and LLM Contributions

This document sets expectations for external tooling used to produce
contributions to this repository. Its focus is AI and LLM tooling, but the
same rules apply to any tool that writes content on a contributor's behalf.

The position here follows the Linux kernel's guidelines for tool-generated
content. Contributions may be produced with tools. Disclosure is expected. The
human submitter is fully responsible for the result.

## Scope

### Out of scope

This repository already specifies its own tooling, and using it requires no
disclosure. Those are the project's own instructions, not external assistance,
and they are whatever [the checks in CI](.github/workflows/ci.yml) and
[the pre-commit hooks](.pre-commit-config.yaml) say at the time.

Applying a formatter, tidying a module graph, or following a written
instruction is not tool-generated contribution in the sense of this document,
even when a tool performs the edit.

Reading the codebase with a lookup tool is likewise not tool-generated
contribution. [godoc-mcp](https://github.com/mrjoshuak/godoc-mcp), which this
project recommends for godoc access, is the expected case.

### In scope

These guidelines apply when a meaningful part of a contribution was not written
by a person, and also when a tool was used to find a problem the change
addresses. Noting the second case gives credit where it is due and helps others
find out which tools are useful.

Examples:

- A coding assistant wrote a new function, or rewrote an existing one.
- A file in the pull request was generated by a tool and then edited by hand.
- A tool found a bug that the pull request fixes.
- A tool wrote the pull request description or the commit message body.
- Text was translated between languages by a tool.
- A model produced a change that went beyond what a formatter would have made,
  so it counts even where the result looks mechanical.

If in doubt, choose transparency and assume these guidelines apply.

## Disclosure

Say in the pull request description what tools were involved. More detail helps
review and costs little:

- Which tools were used, and which model, if you are able to say.
- The prompts, if the change came from a single prompt or a short session. For
  a longer session, summarise the prompts and the assistance given.
- Which parts of the change came from the tool, if only some of it did.
- How the change was tested, and with what.

The disclosure belongs in the pull request, where a reviewer will see it. A
commit message body is acceptable when the pull request description points at
it.

## Attribution

Adding a trailer helps track how much of the project depends on which tools.
Add one when a tool contributed:

```
Assisted-by: <tool or model name>
```

One trailer per tool, each on its own line. This is a convention, not a gate.
Nothing in CI checks for it, and a pull request without one is not rejected on
that basis. If no attribution is appropriate, leave it out.

A generated commit message should describe what the change does, not that a tool
produced it. The trailer is where the latter belongs. The message format itself
is in [CONTRIBUTING.md](CONTRIBUTING.md).

## Responsibility

The person who opens the pull request is the submitter and owns it completely.

- They must be able to explain every line they are submitting.
- They must be able to respond to review comments about it without handing the
  question to a tool and pasting the answer back.
- They must have verified the claims the change makes. Tool output that was not
  run is not evidence.

A machine cannot certify anything on a human's behalf. This repository has no
Developer Certificate of Origin and no sign-off flow, so there is no tag to
delegate. What matters is the principle behind those systems: the human asserts
the work is theirs. An assistant must never add a sign-off, a licence grant, or
any other certification on a contributor's behalf.

If you cannot defend a change, do not submit it.

## Review

Maintainers have discretion over how a tool-assisted contribution is handled.
They may:

- Review it like any other contribution.
- Ask for extra testing, or for the change to be broken into smaller pieces.
- Ask you to explain the code in more detail, to confirm you understand it.
- Ask how the tool or model was trained, or configured.
- Ask for a better prompt rather than proposing specific changes.
- Decline the change, for reasons disclosed or otherwise.

Expect scrutiny in proportion to how much of the change was generated. Nothing
here is grounds for automatic rejection, and nothing here entitles a
contribution to less review than a human-written one.

## Working in this repository

[CONTRIBUTING.md](CONTRIBUTING.md) covers the mechanics: what to read before
editing, which checks to run and report, the boundaries of a good diff, and
commit message format. Those rules apply equally to a change written by hand
and one written with assistance.

Nothing in this document lowers or raises that bar. A tool is never a reason to
skip a step, and never a reason to submit less than you can defend.

## Licensing

Tool output is not automatically compatible with this project's licence, and a
licence question the submitter cannot answer is a reason not to submit. The rule
about code whose origin you cannot account for is in
[CONTRIBUTING.md](CONTRIBUTING.md); it is not specific to tooling.

One case is specific. If a tool suggests code that looks derived from a source
under a copyleft or other restrictive licence, say so and let a maintainer
decide. A tool is good at reproducing the shape of code it has seen and bad at
recalling where it saw it.
